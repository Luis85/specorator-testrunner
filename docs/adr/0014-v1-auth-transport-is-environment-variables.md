# V1 Auth Transport Is Environment Variables

The plugin owns the transport for SUT credentials — it injects per-Environment key/value pairs into the runner subprocess as environment variables. The plugin does **not** own the login mechanism. The user's step definitions read `process.env.E2E_USERNAME` (or any other key the user names) and call the SUT however that SUT expects.

```ts
interface SutEnvironment {
  baseUrl: string;
  auth?: SutAuth;                          // demo has none
}

interface SutAuth {
  env: Record<string, string>;             // injected verbatim into the runner
}
```

Locally, values come from `SutEnvironment.auth.env` (V1 stores them in plaintext in plugin data — see SDD AD-9). In CI, the workflow generated by `PipelineGenerationService` reads the same keys from `secrets.E2E_*`. The contract is identical in both environments.

Login mechanisms vary too much across real-world systems (form, bearer, OAuth, federated, MFA, captcha bypass, CSRF dance, magic links). Generalising the mechanism inside the plugin would be wrong half the time. Letting the user write the login step keeps the plugin out of the auth-flow business while still solving the actual hard part — distributing credentials safely from the same place to local and CI.

## Considered alternatives

- **Auth provider abstraction with built-in adapters (basic / bearer / form / OAuth).** Highest out-of-box value. Rejected: every real-world auth flow has a non-obvious twist; our adapter would frequently be wrong.
- **First-class programmatic-login primitive.** Plugin generates a `support/auth.ts` template with a `login(page, credentials)` signature, runs as a `Before` hook on `@authenticated` scenarios. Rejected: opinionated about login pattern; user is going to throw it away.
- **Playwright `storageState.json` pattern.** Global-setup logs in once, persists session to disk, reused across scenarios. Rejected: ties to cookie/localStorage-based sessions and conflates session storage with credentials.
- **Out of scope for V1.** Users hand-write everything. Rejected: same problem hits every user on day one.

## Consequences

- `SutEnvironment.auth?: { env: Record<string, string> }` becomes part of the Settings type. The plugin does not interpret keys; only injects them.
- `RunnerCommandBuilder` builds the spawn environment as `{ BASE_URL: <active env baseUrl>, ...<active env auth.env> }`.
- `EnvironmentValidationService.validateCiReadiness()` warns when expected `E2E_*` secrets are missing from the GitHub repo — based on the union of `auth.env` keys across configured Environments.
- The demo Environment has no `auth`; UC-001 happy path never needs credentials. The wedge stays clean.
- Storage of plaintext credentials in plugin data is its own tactical decision recorded as SDD AD-9, not a separate ADR — it can be revisited in V2 (OS keychain, env-var-only, etc.) without changing the transport.
