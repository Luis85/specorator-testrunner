# TD-001 Support escaped pipes (`\|`) in Gherkin table cells

> The V1 cell model cannot represent a literal `|` inside a table cell. Pipe
> handling is currently spread across three lossy layers instead of one escape
> rule.

## Current state

- `parseTableRow` (`src/application/content/gherkin.ts`) splits on every `|`,
  with no `\|` escape support.
- `serialiseCell` (same file) substitutes `/` for literal pipes so a
  programmatically built cell cannot change the table shape.
- `sanitizeCell` (`src/presentation/views/feature-editor-format.ts`) applies
  the same substitution (via `serialiseCell`, since the polishing pass) to
  editor input.
- The round-trip guard compares any table row containing a backslash verbatim,
  so files that already use the official Gherkin `\|` escape fall back to
  raw-text mode permanently.

## Cost

A user with a legitimate pipe in table data (a regex column, a CLI example
like `cmd | grep`) cannot author it in structured mode at all: typing it
silently rewrites to `/`, and a correctly escaped file is locked out of
structured editing forever. Every new code path that builds a cell must
remember to sanitize or it reintroduces the shape-corruption bug.

## Proposed direction

Implement the escape once at the parse/serialize boundary:

1. `parseTableRow` splits on unescaped pipes only and unescapes `\|` → `|`
   (and `\\` → `\`) in cell values.
2. `serialiseCell` re-escapes on the way out instead of substituting `/`.
3. Remove the guard's verbatim-comparison special case for backslash rows
   (it exists only because the model cannot represent the escape).
4. `sanitizeCell` reduces to a trim.

The guard's round-trip corpus tests in `tests/gherkin.test.ts` pin the current
substitution behaviour and must be updated deliberately alongside this change.
