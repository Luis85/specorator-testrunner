# TD-003 Single source of truth for structural Feature validation

> The same structural rules live in two independent implementations that have
> already started to drift.

## Current state

- `DefaultSpecificationService.validate`
  (`src/application/services/specification-service.ts`) implements the
  Validate action's rules: feature name, ≥1 scenario, steps per scenario,
  ADR-0012 `UC-NNN-` filename prefix.
- `projectValidation` (`src/presentation/views/feature-editor-format.ts`)
  re-implements the same rules for the editor's live ✓/✗/! strip, plus
  editor-only hints (unnamed scenario, Outline without Examples rows, step
  with both arguments).

## Cost

The two already diverge on one rule: the service checks
`featureName === ""` (exact empty), the editor checks
`featureName.trim() === ""` (whitespace-only counts too). Every future rule
must be mirrored by hand; the editor strip and the Validate action will
disagree silently until a user notices.

## Proposed direction

Extract a pure `structuralIssues(specification): ValidationItem[]` into the
application layer (next to the parser in `src/application/content/`, or a new
`feature-validation.ts`), consumed by both the service and the editor. The
editor layers its typing-time-only hints on top. Note the layering: the shared
module must NOT live in `presentation/` (the service cannot import upward).

Decide deliberately which empty-name semantics wins (`trim()` is the better
rule) and update the service's tests accordingly.
