# TD-005 Unify the "is this scenario an Outline" predicate

> Three sites answer "is this scenario an Outline?" with two different
> definitions. They are individually defensible but can drift.

## Current state

- `effectiveScenarioTagSets`
  (`src/application/services/feature-insight-service.ts`) treats a scenario as
  an Outline when `keyword === "Scenario Outline"` **or** `examples` is
  present — lenient, so a malformed plain `Scenario:` carrying an `Examples:`
  block (which the lenient parser attaches) is counted per-block.
- `FeatureEditorView.renderScenarioCard` and `projectValidation` use the
  keyword only — a plain scenario with attached examples renders no Examples
  grid and gets no rowless-Outline warning, though the serializer still
  round-trips the blocks faithfully.

## Cost

A scenario parsed with examples but no Outline keyword is counted as an
Outline by suite/tag matching but edited as a plain scenario — dashboard
match counts can disagree with what the editor shows. When the keyword
normalisation rule is next adjusted, only some of the sites will be updated.

## Proposed direction

Export one predicate from the domain entity module
(`src/domain/entities/specification.ts`):

```ts
export const isScenarioOutline = (scenario: ScenarioSpecification): boolean => …
```

and decide ONE semantics deliberately. The decision to make: should a
malformed plain-Scenario-with-Examples count as an Outline (lenient,
Cucumber would reject the file anyway) or should the parser normalise the
keyword at parse time so the question never arises? Normalising at parse time
is the deeper fix but changes round-trip behaviour for malformed files (guard
would fail → raw mode, which is arguably correct).
