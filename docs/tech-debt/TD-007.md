# TD-007 gherkin.ts parser/serializer complexity is suppressed, not solved

> `parseFeature` (cyclomatic 43 / cognitive 81), `serialiseFeature` (19 / 30)
> and `significantLines` (10 / 18) carry `fallow-ignore-next-line complexity`
> suppressions instead of decomposition.

## Current state

The TD-001/TD-002 work (pre-V2 Phase 1) edited `src/application/content/
gherkin.ts`, which pulled its pre-existing complexity into the blocking
audit's scope. The increment's convention is fix-don't-suppress, and every
other hot spot it touched was decomposed (`runInitialization`,
`settings-service` repair/validation, `listKnownTags`); these three were
deliberately suppressed instead.

## Why suppression was the deliberate call

The TD-001/TD-002 increment chose to suppress rather than decompose because
the V2 proposal's §9 Phase 3 was expected to replace this hand-rolled parser
with the **official Gherkin parser** — making decomposition throwaway work.

> **Correction (2026-06-14).** Phase 3 shipped, but it swapped the **runner**
> (bddgen + `playwright test` parse `.feature` files with `@cucumber/gherkin`
> at *execution* time), NOT the plugin's editor parser. The Feature Editor's
> structured mode still depends on this module: `parseFeature` →
> `FeatureSpecification` and `serialiseFeature` back, with a
> `roundTripsLosslessly` guard. `@cucumber/gherkin` parses but does not
> serialise to the editor's lossless round-trip contract, so the hand-rolled
> parser **stays for now**. The "wait for Phase 3" rationale no longer holds —
> do not assume a future migration will delete these functions for free.

## Cost

Every edit to `gherkin.ts` rides past three suppressed findings (`parseFeature`
cyclo 43/cog 81, `serialiseFeature` 19/30, `significantLines` 10/18); a
regression pushing a suppressed function deeper is invisible to the gate. With
the replacement no longer imminent, this is now standing debt, not a short wait.

## Proposed direction

The parser is staying, so the suppressions need an active resolution, not a
migration to wait for. Two real options (decide when `gherkin.ts` next needs
substantive work, or as a dedicated increment):

1. **Decompose in place.** Split `parseFeature`'s line-classification loop into
   per-keyword handlers and lift `serialiseFeature`'s block writers out; the
   round-trip corpus guards the refactor. Removes all three suppressions.
2. **Adopt `@cucumber/gherkin` for parsing, keep a custom serializer.** Parse
   via the official library (deleting `parseFeature`), retain/decompose
   `serialiseFeature` for the lossless editor round-trip. Larger; warrants its
   own ADR if pursued.

Until then the suppressions are accepted, **visible** debt — but treat the
suppressed functions as fix-first targets in any change that touches them.
