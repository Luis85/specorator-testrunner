# TD-007 gherkin.ts parser/serializer complexity is suppressed, not solved

> `parseFeature` (cyclomatic 43 / cognitive 81), `serialiseFeature` (19 / 30)
> and `significantLines` (10 / 18) carry `fallow-ignore-next-line complexity`
> suppressions instead of decomposition.

## Current state

The TD-001/TD-002 work (pre-V2 Phase 1) edited `src/application/content/
gherkin.ts`, which pulled its pre-existing complexity into the blocking
audit's scope. The increment's convention is fix-don't-suppress, and every
other hot spot it touched was decomposed (`runInitialization`,
`settings-service` repair/validation, `listKnownTags`); these three were
deliberately suppressed instead.

## Why suppression was the deliberate call

§9 Phase 3 of the V2 proposal replaces this hand-rolled parser with the
**official Gherkin parser** via playwright-bdd (items 3.1–3.3). Decomposing
`parseFeature` now is high-risk work on code scheduled for replacement —
the round-trip corpus would catch regressions, but the effort is likely
throwaway. The suppressions are visible in the audit output (counted as
suppressed, never silently excluded).

## Cost

Until Phase 3 lands, every edit to `gherkin.ts` rides past three suppressed
critical findings; a regression that pushes a suppressed function further
into complexity is invisible to the gate. The serializer (`serialiseFeature`)
and the round-trip guard survive the Phase 3 swap (we still serialise), so
their two suppressions may outlive the parser replacement.

## Proposed direction

1. Phase 3 (playwright-bdd migration): when `parseFeature` is replaced by
   the official parser, delete it and its suppression.
2. At that point decompose or re-evaluate `serialiseFeature` and
   `significantLines` against the gate threshold; remove the remaining
   suppressions either way.
3. If any `gherkin.ts` work is needed BEFORE Phase 3, treat the suppressed
   functions as fix-first targets in that change, not as licensed debt.
