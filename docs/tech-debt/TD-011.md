# TD-011 Post-run evidence orchestration and Use Case frontmatter writes lack a single seam

> The post-run flow spans three services with caller-visible event ordering, and
> three services write Use Case frontmatter — the "all UC writes serialise"
> invariant is held by convention, not a boundary.

## Current state

Two coupled smells the 2026-06-14 architecture review surfaced (both rated
Strong):

1. **Orchestration without a use-case boundary.** `PostRunCoordinator` →
   `ReportImportService` (`report.imported`) → `EvidenceGenerationService`
   (`evidence.generated`) choreograph "import a finished run's evidence and
   refresh the dashboard" across three services; a caller must understand all
   three contracts and the event ordering to wire it correctly.
2. **Scattered frontmatter writers.** `UseCaseService` (`prd-id`),
   `EvidenceGenerationService` (`evidence`/`last_run`) and the run-recording path
   (`lastTestRun`) each write Use Case frontmatter behind their own
   `KeyedSerialQueue`. The serialisation invariant (frontmatter is the audit
   trail, ADR-0005) is enforced in three places by convention.
   `use-case-service.ts` also repeats the read→mutate→write→publish sequence in
   three internal clones.

## Why deferred

This is behaviour-correct today (the queues do serialise) and the consolidation
is a large, cross-service change. Refactoring pre-emptively risks churn the V2
evidence work would redo.

## Intended direction

EPIC-014 (scenario identity & per-scenario history) and EPIC-015 (audit-grade
evidence) both rework the evidence + frontmatter paths. Consolidate THEN:

- a single **Use Case Persistence** writer that owns the serial queue and is the
  only module that knows the frontmatter shape (`prd-id`, `evidence`,
  `last_run`, `lastTestRun`); this also collapses the three `use-case-service`
  clones;
- a **RunEvidence** pipeline that owns the report→evidence→dashboard sequence,
  reducing `ReportImportService` / `EvidenceGenerationService` to pure
  transform/persist with no orchestration.

Do not refactor ahead of those epics; recorded here so the review stops
re-surfacing it and the epics fold it in.
